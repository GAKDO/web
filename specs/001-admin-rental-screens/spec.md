## Clarifications

### Session 2026-11-02

- Q: 렌탈 종료 버튼은 언제부터 누를 수 있나? → A: 반납 시점의 등급이 나온(GRADED) 뒤(봉인 SEALED 포함). 버튼 상태는 서버가 준 시점 상태로 정하고, 최종 판단은 서버의 409를 따른다.
  - 갱신(같은 날): C1 `rental-server.yaml` closeRental이 "반납(RET) 시점이 봉인된 렌탈만 CLOSED, 아니면 409 RENTAL_NOT_CLOSABLE"로 정해 계약을 따라 SEALED 이후로 바꿨다(헌법 I).
- Q: 폐기한 기기를 화면에서 되돌릴 수 있나? → A: "수리 중"으로만 되돌릴 수 있다(확인 한 번 더). 잘못 누른 폐기라도 점검을 거친 뒤에만 다시 렌탈에 나가게 한다. 사용 가능으로 바로 되돌리는 길은 없다.
- Q: 렌탈을 만들 때 기기 고르는 목록에 수리 중·폐기 기기도 보이나? → A: 평소에는 사용 가능 기기만 보이고, "다른 상태 기기도 보기" 스위치를 켜면 수리 중·폐기 기기가 상태 표시와 함께 나온다. 그 기기를 골라 만들면 서버의 409 문장이 보인다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자 로그인·로그아웃 (Priority: P1)

대여 관리자가 이메일과 비밀번호로 로그인해 관리 화면에 들어가고, 일을 마치면 로그아웃한다. 화면을 새로 고쳐도 다시 로그인하지 않고 이어서 쓸 수 있지만, 로그인 정보는 브라우저 저장소에 남지 않는다.

**Why this priority**: 다른 모든 관리 화면의 입구다. 로그인 없이는 기기·렌탈 화면을 열 수 없다.

**Independent Test**: 관리자 계정으로 로그인 → 관리 첫 화면이 열리고, 로그아웃 → 로그인 화면으로 돌아가는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 로그인 화면, **When** 올바른 관리자 이메일·비밀번호를 넣고 로그인하면, **Then** 기기 목록 화면이 열린다.
2. **Given** 로그인 화면, **When** 틀린 비밀번호로 로그인하면, **Then** "이메일 또는 비밀번호가 맞지 않습니다" 같은 문장이 입력 칸 근처에 보이고 비밀번호 칸만 비워진다.
3. **Given** 로그인 시도가 너무 잦아 서버가 거절하면(429), **When** 다시 로그인하면, **Then** 잠시 뒤 다시 시도하라는 문장이 보인다.
4. **Given** 로그인한 상태, **When** 액세스 토큰이 만료된 뒤 화면을 쓰면, **Then** 화면이 스스로 토큰을 다시 받아 하던 일이 끊기지 않는다.
5. **Given** 로그인한 상태, **When** 다시 받기도 실패하면(리프레시 만료), **Then** 로그인 화면으로 가고 "다시 로그인해 주세요"가 보인다.
6. **Given** 로그인한 상태, **When** 로그아웃하면, **Then** 로그인 화면으로 가고 뒤로 가기로 관리 화면을 다시 볼 수 없다.
7. **Given** 고객(CUSTOMER) 계정, **When** 관리 화면에 로그인하면, **Then** 관리자 전용이라는 문장이 보이고 관리 화면은 열리지 않는다.
8. **Given** 로그인한 상태, **When** 브라우저 저장소(localStorage·sessionStorage)를 보면, **Then** 액세스 토큰이 없다.

### User Story 2 - 기기 목록·검색·상태 바꾸기 (Priority: P1)

관리자가 기기 목록을 기종·상태로 거르고 시리얼·자산번호 일부로 찾은 뒤, 기기 상태를 사용 가능·수리 중·폐기로 바꾼다.

**Why this priority**: FR-RNT-05의 화면 그 자체이고, 렌탈을 만들 기기를 고르는 출발점이다.

**Independent Test**: 목 데이터 기기 몇 대로 거르기·검색·상태 바꾸기를 해 보고 목록에 바로 반영되는지 본다.

**Acceptance Scenarios**:

1. **Given** 기기 목록, **When** 기종을 고르면, **Then** 그 기종의 기기만 보인다.
2. **Given** 기기 목록, **When** 상태(사용 가능·수리 중·폐기)를 고르면, **Then** 그 상태의 기기만 보인다.
3. **Given** 기기 목록, **When** 검색 칸에 시리얼이나 자산번호 일부를 넣으면, **Then** 맞는 기기만 보인다.
4. **Given** 사용 가능 기기, **When** 상태를 수리 중으로 바꾸면, **Then** 목록의 상태가 바로 바뀐다.
5. **Given** 진행 중인 렌탈이 있는 기기, **When** 수리 중이나 폐기로 바꾸면, **Then** 서버의 409가 "진행 중인 렌탈이 있어 상태를 바꿀 수 없습니다. 렌탈을 먼저 종료하세요" 같은 사람이 읽는 문장으로 보이고 상태는 그대로다.
6. **Given** 폐기로 바꾸려는 기기, **When** 바꾸기를 누르면, **Then** 확인 창이 먼저 뜨고, 폐기 뒤에도 그 기기는 목록(폐기 거르기)에 남는다.
8. **Given** 폐기 기기, **When** 상태 메뉴를 열면, **Then** "수리 중으로 되돌리기"만 고를 수 있고, 확인 창 뒤 상태가 수리 중으로 바뀐다. "사용 가능"은 고를 수 없다.
7. **Given** 기기 상세, **When** 색상·자산번호·OS를 고치면, **Then** 저장되고, 시리얼·기종은 고칠 수 없게 보인다.

### User Story 3 - 기종·기기 등록 (Priority: P2)

관리자가 새 기종(이름·제조사·치수·기준 사양)을 등록하고, 그 기종으로 새 기기(시리얼·OS·색상·자산번호)를 등록한다.

**Why this priority**: 시연 전에 기기를 넣어야 하지만, 초기 데이터로 대신할 수도 있어 P1 다음이다.

**Independent Test**: 기종 하나를 등록하고 그 기종으로 기기 하나를 등록한 뒤 목록에 나오는지 본다.

**Acceptance Scenarios**:

1. **Given** 기기 등록 화면, **When** 기종 선택 목록을 열면, **Then** 등록된 기종이 모두 보인다.
2. **Given** 기기 등록 화면, **When** 이미 있는 시리얼로 등록하면, **Then** 409가 "이미 등록된 시리얼입니다" 같은 문장으로 보인다.
3. **Given** 기종 등록 화면, **When** 치수 칸을 비우거나 숫자가 아니게 넣으면, **Then** 보내기 전에 어느 칸이 왜 틀렸는지 보인다.
4. **Given** 기종 등록 화면, **When** 이미 있는 기종 코드로 저장하면, **Then** 그 기종의 정보가 고쳐진다(등록·수정 같은 동작).

### User Story 4 - 렌탈 만들기와 출고·수령·반납 시점 진행 (Priority: P1)

관리자가 사용 가능한 기기와 대여자 참조 번호로 렌탈을 만들고, 출고(OUT) → 수령(RCV) → 반납(RET) 시점을 순서대로 시작하며, 반납 뒤 렌탈을 종료한다. 각 시점의 상태(열림·촬영됨·등급 매김·봉인)를 렌탈 상세에서 본다.

**Why this priority**: 세 시점 흐름 시연의 뼈대다. 수용 기준의 409 문장이 여기서 나온다.

**Independent Test**: 렌탈 하나를 만들어 출고 → 수령 → 반납 시작 → (반납 기록이 봉인된 뒤) 종료까지 누르고, 각 단계에서 상세의 시점 상태가 바뀌는지 본다.

**Acceptance Scenarios**:

1. **Given** 사용 가능 기기, **When** 대여자 참조 번호를 넣고 렌탈을 만들면, **Then** 렌탈 상세가 열리고 출고 시점 시작 버튼만 누를 수 있다.
1-1. **Given** 렌탈 만들기 화면, **When** 기기 고르는 목록을 열면, **Then** 사용 가능 기기만 보이고, "다른 상태 기기도 보기"를 켜면 수리 중·폐기 기기가 상태 표시와 함께 보인다.
2. **Given** 수리 중 기기(스위치를 켜고 고름), **When** 그 기기로 렌탈을 만들면, **Then** 서버의 409가 "이 기기는 수리 중이라 렌탈을 만들 수 없습니다" 같은 사람이 읽는 문장으로 보인다. (수용 기준)
3. **Given** 폐기 기기, **When** 그 기기로 렌탈을 만들면, **Then** 서버의 409가 "이 기기는 폐기되어 렌탈을 만들 수 없습니다" 같은 문장으로 보인다. (수용 기준)
4. **Given** 진행 중인 렌탈이 있는 기기, **When** 또 렌탈을 만들면, **Then** 409가 "이 기기로 진행 중인 렌탈이 이미 있습니다" 같은 문장과 "진행 중인 렌탈 보기"(진행 중으로 거른 렌탈 목록) 링크로 보인다. (409 응답에 그 렌탈 ID가 없어 바로 가는 길은 없다)
5. **Given** 출고 시점이 없는 렌탈, **When** 화면에서 수령·반납 시작을 찾으면, **Then** 그 버튼은 누를 수 없고 왜 안 되는지(출고 먼저) 보인다.
6. **Given** 화면 상태가 오래돼 순서가 어긋난 요청을 보내면, **When** 서버가 409(순서 위반)를 돌려주면, **Then** 사람이 읽는 문장이 보이고 렌탈 상세를 다시 읽어 최신 상태를 보여 준다.
7. **Given** 반납 시점이 봉인된(SEALED) 렌탈, **When** 렌탈 종료를 누르면, **Then** 확인 창 뒤 렌탈이 종료 상태로 보인다.
9. **Given** 반납 시점이 열렸지만 아직 봉인되지 않은(OPEN·CAPTURED·GRADED) 렌탈, **When** 상세를 보면, **Then** 종료 버튼은 꺼져 있고 "반납 기록이 봉인되면 종료할 수 있습니다"와 지금 시점 상태가 보인다.
10. **Given** 화면은 종료할 수 있다고 봤지만 서버가 종료를 409로 거절하면, **When** 종료를 누르면, **Then** 서버 문장이 보이고 상세를 다시 읽어 버튼 상태를 맞춘다.
8. **Given** 렌탈 목록, **When** 화면을 열면, **Then** 렌탈마다 기기 시리얼·기종·렌탈 상태·만든 날이 보인다. (대여자 참조 번호·지금 시점은 C1 `RentalSummary`에 없어 상세에서 보인다. 더하는 변경을 요청함)

### Edge Cases

- 서버에 닿지 않거나 5xx가 오면 "잠시 뒤 다시 시도해 주세요"와 다시 시도 버튼을 보여 주고, 입력한 값은 지우지 않는다.
- 서버가 알 수 없는 오류 코드를 주면 Problem Details의 `detail`을 보여 주고, 그것도 없으면 일반 문장을 보여 준다(빈 화면이나 영문 스택을 보여 주지 않는다).
- 같은 버튼을 빠르게 두 번 누르면 요청은 한 번만 간다(처리 중에는 버튼을 잠근다).
- 다른 관리자가 그사이 기기 상태를 바꿨으면, 저장 실패(409) 뒤 목록을 다시 읽는다.
- 반납 기록이 오래 봉인되지 않으면(검사·등급·봉인 지연이나 실패) 종료 버튼은 계속 꺼진 채로 두고, 상세를 다시 읽는 버튼과 "반납 기록이 아직 봉인되지 않았습니다. 잠시 뒤 다시 불러오세요" 안내를 보여 준다. 화면에서 강제로 종료하는 길은 두지 않는다.
- 기기·렌탈이 0건이면 빈 목록 대신 "등록된 기기가 없습니다 · 기기 등록" 안내를 보여 준다.
- 375px에서는 표 대신 카드 목록으로 보이고, 가로 스크롤 없이 모든 버튼을 누를 수 있다.
- 새 탭을 열면 그 탭도 로그인 상태를 이어받는다(리프레시 쿠키로 다시 받음). 브라우저를 닫았다 열면 리프레시가 살아 있는 동안 이어진다.

## Requirements *(mandatory)*

### Functional Requirements

**로그인 (FR-AUTH-01 화면)**

- **FR-001**: 화면은 관리자가 이메일·비밀번호로 로그인하게 MUST 한다.
- **FR-002**: 액세스 토큰은 화면 메모리에만 두고 localStorage·sessionStorage·IndexedDB·읽을 수 있는 쿠키에 MUST NOT 저장한다.
- **FR-003**: 화면을 새로 고치거나 새 탭을 열면, 서버가 준 리프레시 쿠키로 액세스 토큰을 다시 받아 로그인을 이어 MUST 간다. 실패하면 로그인 화면으로 간다.
- **FR-004**: 요청이 401로 실패하면 한 번만 토큰을 다시 받아 같은 요청을 다시 보내고, 다시 실패하면 로그인 화면으로 MUST 보낸다. 동시에 여러 요청이 401이 나도 다시 받기는 한 번만 한다.
- **FR-005**: 로그아웃하면 서버에 로그아웃을 알리고 메모리의 토큰과 화면에 캐시한 서버 데이터를 MUST 비운다.
- **FR-006**: 관리자가 아닌 계정으로는 관리 화면을 MUST NOT 연다.

**기기·기종 (FR-RNT-05·03 화면)**

- **FR-010**: 기기 목록을 기종·상태로 거르고, 시리얼·자산번호 일부로 MUST 찾는다. 결과가 많으면 다음 쪽을 불러올 수 있다.
- **FR-011**: 기기 상태를 바꿀 수 MUST 있다. 사용 가능 ↔ 수리 중은 자유롭게, 사용 가능·수리 중 → 폐기는 확인을 한 번 더 받고, 폐기 → 수리 중은 확인을 한 번 더 받는다. 폐기 → 사용 가능은 화면에 없다.
- **FR-012**: 기기의 색상·자산번호·OS를 고칠 수 MUST 있고, 시리얼·기종은 등록 뒤 고칠 수 없게 보여야 한다.
- **FR-013**: 기종 목록에서 고른 기종으로 새 기기(시리얼·OS, 선택으로 색상·자산번호)를 MUST 등록한다.
- **FR-014**: 기종(코드·이름·제조사·치수 4개·기준 사양)을 등록하거나 고칠 수 MUST 있다. 치수는 0보다 큰 숫자(mm)여야 한다.
- **FR-015**: 상태·OS·형태 같은 코드 값은 contracts `codes.yaml`의 값만 쓰고, 화면에는 한국어 이름(사용 가능·수리 중·폐기 등)으로 MUST 보인다.

**렌탈·시점 (FR-RNT-01·02 흐름)**

- **FR-020**: 기기와 대여자 참조 번호로 렌탈을 MUST 만든다. 대여자 실명은 받지 않는다. 기기 고르는 목록은 기본으로 사용 가능 기기만 보이고, 스위치로 수리 중·폐기 기기도 상태 표시와 함께 볼 수 있다(그 기기로 만들면 서버 409를 FR-031대로 보인다).
- **FR-021**: 렌탈 목록(계약 `RentalSummary`의 시리얼·기종·렌탈 상태·만든 날)과 상세(대여자 참조 번호·렌탈 상태·세 시점 상태)를 MUST 보여 준다. 목록에 대여자 참조 번호·지금 시점을 더하는 것은 계약이 더해진 뒤에 한다(c1-questions 4).
- **FR-022**: 시점은 출고 → 수령 → 반납 순서로만, 앞 시점이 봉인(SEALED)된 뒤에만 시작할 수 있게 다음 버튼만 열어 두고(11/02 C 결정, 서버 동작은 A 확인 중 — c1-questions 11), 서버가 순서 위반(409)을 주면 문장을 보여 준 뒤 상세를 다시 MUST 읽는다.
- **FR-023**: 반납 시점이 SEALED인 렌탈만 확인을 받은 뒤 MUST 종료할 수 있다. 버튼을 켤지는 서버가 준 시점 상태로만 정하고(화면이 따로 상태를 지어내지 않음), 서버가 409로 거절하면 그 문장을 보이고 상세를 다시 읽는다.

**오류·화면 공통**

- **FR-030**: 서버의 Problem Details 오류는 `code`별로 정한 한국어 문장(무엇이 잘못됐고 어떻게 하면 되는지)으로 MUST 보인다. 정하지 않은 `code`는 `detail`, 그것도 없으면 일반 문장을 보인다.
- **FR-031**: 수리 중·폐기 기기로 렌탈을 만들 때 오는 409는 기기 상태를 밝힌 문장으로 MUST 보인다. (수용 기준)
- **FR-032**: 모든 화면은 375px과 1280px 폭에서 가로 스크롤 없이 모든 기능을 MUST 쓸 수 있다.
- **FR-033**: 모든 입력과 버튼에 레이블이 MUST 있고, 처리 중에는 같은 버튼을 다시 누를 수 없다.
- **FR-034**: 서버 API 모양(요청·응답·오류 코드)은 화면 코드 한 곳에 모아 두고, contracts C1 OpenAPI(`openapi/*-server.yaml`)에서 만들고, 계약이 바뀌면 그곳만 다시 만들어 MUST 맞춘다. 서버가 준비되기 전까지는 같은 계약을 따르는 흉내 낸 서버 응답으로 개발·테스트한다.
- **FR-035**: 화면·주소(URL)·흉내 낸 데이터에 쓰는 ID는 모두 publicId(NanoID 21자 문자열)이고, DB 내부 숫자 id는 MUST NOT 다루거나 보인다(헌법 1.1.0).

### Key Entities *(include if feature involves data)*

- **관리자 세션**: 로그인한 관리자의 메모리 안 액세스 토큰, 역할, 만료 시각. 저장소에 남지 않는다.
- **기종(Device Model)**: 기종 코드(예: MBA13-M2), 이름, 제조사, 형태(CLAMSHELL), 기준 사양(CPU·RAM·SSD), 3D 치수(가로·깊이·본체 높이·덮개 높이 mm).
- **기기(Device)**: 시리얼(신원, 고칠 수 없음), 기종, OS(MACOS·WINDOWS), 색상, 자산번호, 상태(ACTIVE 사용 가능·MAINTENANCE 수리 중·RETIRED 폐기), 폐기 시각.
- **렌탈(Rental)**: 기기, 대여자 참조 번호, 상태(OPEN·RETURNED·CLOSED), 시작·종료 시각, 시점 셋.
- **시점(Checkpoint)**: 종류(OUT 출고·RCV 수령·RET 반납), 상태(OPEN·CAPTURED·GRADED·SEALED), 일어난 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 쓰는 관리자가 설명 없이 로그인 → 렌탈 만들기 → 출고 시점 시작까지 2분 안에 끝낸다.
- **SC-002**: 수리 중·폐기 기기로 렌탈을 만들 때 보이는 문장을 읽은 사람 3명 중 3명이 왜 안 되는지와 무엇을 해야 하는지 말한다.
- **SC-003**: 375px과 1280px에서 모든 사용자 이야기의 수용 시나리오를 가로 스크롤 없이 끝낼 수 있다.
- **SC-004**: 로그인 뒤 브라우저 저장소 어디에도 액세스 토큰이 남지 않는다(자동 테스트로 확인).
- **SC-005**: 수용 시나리오마다 자동 테스트가 하나씩 있고 모두 통과한다.
- **SC-006**: 기기 100대 목록에서 검색 결과가 1초 안에 보인다.

## Assumptions

- 관리자 계정은 초기 데이터로 만들어져 있고(decisions.md 5번), 이 화면에는 관리자 가입·비밀번호 재설정이 없다.
- 리프레시 토큰은 서버가 HttpOnly 쿠키(7일)로 주고 화면은 읽지 못한다. "토큰을 오래 저장하지 않는다"는 화면이 액세스 토큰을 저장소에 쓰지 않는다는 뜻으로 읽었다. 7일 쿠키 수명은 서버(AU1)가 정한다.
- 고객 화면(WE3)과 같은 앱에 있지만 이 기능은 관리 화면만 만든다. 고객이 로그인하면 관리자 전용 안내만 보인다.
- 수령(RCV) 시점은 관리자가 시작하고, 고객의 폰 촬영 자체는 WE2가 한다. 부스 촬영 진행률(SSE)과 시점별 검사 결과·리포트 보기는 WE3·WE4·관리자 리포트 몫이다.
- 기기 삭제는 없다(폐기로만 바꾼다).
- C1(OpenAPI 5개)이 2026-11-02 contracts develop에 머지됐다. 흉내 낸 서버 응답과 오류 `code`(codes.yaml `error_code`)는 C1을 따른다. 다만 이날 기준 C1의 ID 형식은 아직 UUID라, 헌법 1.1.0대로 publicId(NanoID 21자)로 바뀐 계약을 기다린다.
- 기기 목록은 C1대로 커서 방식(`limit`·`cursor`)이다.
- 시각은 서버가 UTC 오프셋으로 주고 화면은 한국 시간으로 보인다.
- 수령 QR 링크(capture-links)·에이전트 페어링 코드(pairing-codes) 발급 화면은 WE1에 넣지 않는다(2026-11-02 결정). 출고 때 기기는 목록에서 고르므로 QR이 필요 없다. QR은 수령 시점에 고객 폰 촬영(WE2)을 여는 데, 페어링 코드는 진단 에이전트(AG1)를 붙이는 데 쓴다. 두 화면은 렌탈 상세에 붙는 작은 후속 작업으로 WE2(11/8)와 함께 만들고, 서버는 AU3(11/9)를 따른다. 세 시점 시연(11/10)에는 둘 다 필요하다.

## Risks

- 렌탈 종료는 반납 시점의 봉인(SEALED)에 달려 있어, 검사·봉인 파이프라인(부스 탐지 BO2 → inspect-worker ML2 → 등급 CA2 → 해시 체인 봉인 RP1)이 늦거나 실패하면 11/10 시연에서 반납 → 종료 단계가 막힌다. 화면은 꺼진 버튼과 안내만 보이므로, 시연 전 리허설에서 반납 봉인까지 도는지 확인하고 막히면 A(ML2·CA2)와 대안을 정한다.
- 폐기 되돌리기(RETIRED → MAINTENANCE만)는 화면 쪽 결정이고 C1에는 규칙이 없다. 서버가 다르게 정하면 서버를 따른다.
