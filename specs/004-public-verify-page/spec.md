# Feature Specification: 공개 검증 페이지 (WE4 앞부분)

**Feature Branch**: `claude/project-thread-jrshvh` (Spec Kit 기본 이름은 `feature/004-public-verify-page`. 이 세션은 지정 브랜치만 푸시할 수 있어 이름을 바꿈)

**Created**: 2026-11-02

**Status**: Draft

**Input**: User description: "리포트의 검증 QR로 여는 공개 검증 페이지(등급·시점·해시 일치)를 만든다(FR-INT-02). 수용 기준: QR로 검증 결과 페이지가 열리고, 기록이 바뀌었으면 불일치를 보여 준다." (backlog WE4 중 검증 페이지. 파일럿 대시보드 FR-PIL-02는 다른 명세로 나눈다)

**관련 요구사항**: FR-INT-02(화면), FR-INT-03(검증 응답을 보여 주는 부분)

**의존**: report-server RP1 `GET /api/v1/verify/{verifyToken}` (contracts `openapi/report-server.yaml` operationId `verifyRecord`). RP1은 11/7 예정이라 그 전에는 MSW 목으로 만든다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - QR로 검증 결과 보기 (Priority: P1)

리포트를 받은 사람(고객, 다음 대여자, 중고 구매자 등 누구든)이 리포트의 검증 QR을 폰 카메라로 찍으면, 로그인 없이 검증 페이지가 열린다. 페이지 맨 위에 "기록이 그대로입니다"(정상) 또는 "기록이 바뀌었습니다"(불일치)가 크게 보이고, 아래에 기종 이름과 시점(출고·수령·반납)마다 등급·지문(해시 줄임)·봉인 시각이 나온다.

**Why this priority**: FR-INT-02의 수용 기준 그 자체다. 이 화면이 없으면 해시 체인을 밖에서 확인할 방법이 없다.

**Independent Test**: 목에 정상 토큰을 두고 `/verify/<토큰>`을 열어 정상 표시·기종·시점 2개가 보이는지 확인한다.

**Acceptance Scenarios**:

1. **Given** 봉인된 시점이 있는 렌탈의 검증 주소, **When** 로그인하지 않은 채 열면, **Then** 정상 표시, 기종 이름, 시점 순서대로 시점 이름·등급·지문·봉인 시각, 확인한 시각이 보인다.
2. **Given** 검증 페이지, **When** 지문을 보면, **Then** 앞 4자…뒤 4자로 줄여 보이고, 눌러서 전체 64자를 보거나 복사할 수 있다.
3. **Given** 등급이 아직 없는 시점(grade = null), **When** 보면, **Then** "등급 없음"으로 보이고 화면이 깨지지 않는다.
4. **Given** 검증 페이지, **When** 375px 폰과 1280px 화면에서 열면, **Then** 가로 스크롤 없이 모두 읽힌다.

### User Story 2 - 기록이 바뀌었으면 불일치 보기 (Priority: P1)

서버가 체인 검사에 실패했다고 답하면(valid = false), 페이지가 정상처럼 보이면 안 된다. 맨 위에 경고 색으로 "기록이 바뀌었습니다. 이 리포트를 믿지 마세요" 같은 문장이 보이고, 그래도 서버가 준 시점 목록은 참고용으로 아래에 보인다.

**Why this priority**: 수용 기준의 두 번째 절반이다. 정상만 보여 주는 페이지는 검증 페이지가 아니다.

**Independent Test**: 목에 불일치 토큰을 두고 열어 경고가 보이고 정상 문구가 없는지 확인한다.

**Acceptance Scenarios**:

1. **Given** valid = false 응답, **When** 페이지를 열면, **Then** 경고 표시가 맨 위에 보이고 "그대로입니다" 문구는 어디에도 없다.
2. **Given** 불일치 화면, **When** 시점 목록을 보면, **Then** 목록 위에 "서버가 가진 기록을 그대로 보여 줍니다(참고용)"가 보인다.

### User Story 3 - 잘못된 QR·서버 오류 (Priority: P2)

토큰이 없거나 형식이 틀리거나(32자 소문자 16진수가 아님), 서버가 404를 주면 "검증할 기록을 찾을 수 없습니다"를 보여 준다. 서버에 닿지 못하거나 5xx면 "지금 확인할 수 없습니다. 잠시 뒤 다시 열어 주세요"와 다시 시도 버튼을 보여 준다. 어느 경우에도 "정상"처럼 보이면 안 된다.

**Why this priority**: QR이 찢기거나 잘못 찍히는 일은 흔하다. 다만 정상·불일치 표시보다는 뒤다.

**Independent Test**: 형식이 틀린 토큰, 404 토큰, 500을 주는 목으로 각각 열어 문장을 확인한다.

**Acceptance Scenarios**:

1. **Given** 형식이 틀린 토큰, **When** 열면, **Then** 서버를 부르지 않고 "찾을 수 없습니다"가 보인다.
2. **Given** 서버 404, **When** 열면, **Then** "찾을 수 없습니다"가 보인다.
3. **Given** 서버 500 또는 연결 실패, **When** 열면, **Then** "지금 확인할 수 없습니다"와 다시 시도 버튼이 보이고, 누르면 다시 부른다.
4. **Given** 불러오는 중, **When** 보면, **Then** "확인하는 중" 표시만 보이고 정상·불일치 표시는 아직 없다.

### Edge Cases

- 시점이 1개(출고만 봉인)거나 3개(출고·수령·반납) 모두 같은 화면에서 보여야 한다.
- 서버가 seq 순서를 섞어 보내도 화면은 seq 오름차순으로 보인다.
- 로그인한 관리자가 같은 주소를 열어도 공개 응답만 보인다(토큰을 붙여 보내지 않는다).
- 응답에 계약에 없는 필드가 와도 화면에 그대로 찍지 않는다(개인정보가 섞여 와도 노출되지 않게).
- 시각은 한국 시간으로 "2026. 11. 12. 09:00"처럼 보인다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: `/verify/:verifyToken` 경로를 로그인 없이 연다. 주소 모양은 계약 예시 `https://<web>/verify/<32자 토큰>`을 따른다.
- **FR-002**: 화면은 `GET /api/v1/verify/{verifyToken}`만 부르고, Authorization 헤더를 붙이지 않는다.
- **FR-003**: `valid`가 true면 정상, false면 불일치를 맨 위에 보이며, 두 상태는 색만이 아니라 문구·아이콘으로도 구분된다.
- **FR-004**: 기종 이름(`modelName`)과 시점 목록(seq 오름차순: 시점 이름·등급·지문 줄임·봉인 시각), 확인한 시각(`checkedAt`)을 보인다.
- **FR-005**: 지문은 줄여 보이고 전체 값을 펼치거나 복사할 수 있다.
- **FR-006**: 토큰 형식이 틀리면 서버를 부르지 않고 "찾을 수 없습니다"를 보인다. 404도 같다.
- **FR-007**: 연결 실패·5xx는 "지금 확인할 수 없습니다"와 다시 시도 버튼을 보인다.
- **FR-008**: 응답에서 계약 필드(valid·modelName·records·checkedAt)만 화면에 쓴다.
- **FR-009**: 시점 이름·등급 표시는 codes.yaml 값의 한국어 이름표를 쓰고, 값은 contracts OpenAPI에서 만든 타입에서만 온다.
- **FR-010**: 375px·1280px에서 가로 스크롤 없이 쓸 수 있다.
- **FR-011**: RP1 전에는 MSW 목으로 정상·불일치·404·500을 재현하고, 목과 API 타입은 `src/shared/api`·`src/shared/mocks`의 기존 구조에 한 곳으로 더한다.

### Key Entities

- **검증 결과(VerifyResponse)**: 체인 정상 여부, 기종 이름, 시점 기록 목록, 확인 시각. 개인정보·사진·진단 상세는 없다.
- **시점 기록(VerifyRecord)**: 순번, 시점 종류(OUT·RCV·RET), 등급(없을 수 있음), 지문(SHA-256), 봉인 시각.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: QR을 찍고 3초 안에 정상/불일치가 보인다(학교 망, 폰 기준).
- **SC-002**: 불일치 응답에서 "그대로입니다" 문구가 한 번도 보이지 않는다(테스트로 확인).
- **SC-003**: 정상·불일치·404·형식 오류·500 다섯 경우가 자동 테스트로 덮인다.
- **SC-004**: 실제 report-server(RP1 머지 뒤)의 검증 주소로 열어 정상이 보이고, 기록 하나를 바꾼 렌탈에서 불일치가 보인다.

## Assumptions

- "해시 일치" 판정은 서버(RP1)가 한다. 화면이 서명을 직접 다시 검사하지 않는다(공개 키 배포가 계약에 없음).
- 서버 응답은 렌탈 전체에 대해 `valid` 하나만 준다. 어느 시점이 바뀌었는지는 계약에 없어 화면에서 짚지 못한다.
- 리포트에 QR을 붙이는 일(verifyUrl을 QR로 그리기)은 WE3 고객 리포트 화면 몫이고, 이 명세는 QR이 여는 페이지만 다룬다.
- 파일럿 대시보드(FR-PIL-02)는 다른 명세다.
